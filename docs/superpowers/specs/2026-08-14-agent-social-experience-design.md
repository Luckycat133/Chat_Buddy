## 2. 用户目标与优先级

用户要求同时提升任务 Agent 和社交虚拟角色，而不是只做请求压缩：

- 修复已有问题并进行真实网页体验测试。
- 实际与任务 Agent、虚拟角色对话，验证能力、工具调用和长期记忆。
- Provider 使用 OpenRouter，固定一个合适模型，避免自动路由和多模型 fallback 扇出。
- 保留足够长的上下文和正常模型能力；节省应来自减少无意义请求、重复提示和 fan-out，而不是牺牲用户任务质量。
- 优化 6 个任务 Agent 的对话体验，并增加真正可用、结果可验证的工具。
- 优化 13 个社交角色的差异化人格、连续记忆和互动节奏。
- 角色应像真人但稍微被动；例如用户说“我明天考试”，角色可在第二天晚上主动问“考得怎么样”。
- 支持类似微信的后台通知和逐聊天静音。
- 可以增加后台，并采用“匿名设备默认可用、以后可选登录并合并同步”的混合身份模式。
- 后台可以合理唤醒模型；模型可以自己决定不行动、私聊问候、事件跟进或发朋友圈。
- 主动行为要加入受约束的随机性，模拟真实作息和互动，不得变成机械定时提醒。

## 3. 当前实现基线（已核对）

### 3.1 当前产品与 Provider

- 当前仓库是 React/Vite PWA，主要聊天与设置保存在浏览器本地；没有可供后台自主活动使用的应用服务器或账号系统。
- 当前分支已经把默认 Provider 固定为 OpenRouter 的单一免费模型，并移除了自动 fallback；详见[中文 README](../../../README.zh-CN.md)和[综合审查报告](../../CODE_REVIEW_REPORT_2026-08-11.md)。
- 普通角色/Agent 回合预算为 1 次文本模型请求；确需模型判断工具参数的可见函数调用流程最多 2 次。
- 当前上下文上限为最多 48 条近期消息 / 100,000 字符，按任务提供 1,600～6,144 completion tokens；最多注入 8 条相关耐久事实。
- 当前“朋友圈后台内容”被改成本地生成、零模型请求。这是已有请求优化结果，不是本次新自主社交方案的最终形态。

### 3.2 任务 Agent

[任务 Agent 定义](../../../src/data/taskAgents.js)中目前有 6 个角色：

| Agent | 当前主要定位 | 当前工具状态摘要 |
|---|---|---|
| Coder / 代码 | 编程、调试、代码审查 | 声明 `run_code`、`search_docs`、`analyze_code`，但 `toolsEnabled: false`；不得把声明当成可用能力 |
| Muse / 缪斯 | 创作、润色、翻译 | 声明语法检查和沉浸式翻译；需要重新界定哪些是单次回复能力、哪些是真工具 |
| Scholar / 学者 | 联网研究、事实核查 | 已有 Tavily 检索、深度研究和事实核查路径，是当前最接近真实工具型 Agent 的角色 |
| Sensei / 先生 | 教学、测验、学习进度、数学 | 已有本地测验/学习工具和确定性数学路径 |
| Aurora / 欧若拉 | 情感支持、呼吸练习、情绪追踪 | 声明呼吸与情绪工具，但 `toolsEnabled: false`；情绪记录尚未形成可靠持久数据产品 |
| Pixel / 像素 | 视觉创意、配色、图片 | 已有 MiniMax 图片生成和本地配色能力 |

工具执行入口位于[工具服务](../../../src/features/chat/services/toolService.js)，授权、意图匹配和请求预算主要位于 [AIPipeline](../../../src/core/chat/AIPipeline.js)。当前仍需要逐项验证“声明、授权、实现、UI 展示、真实结果”是否一致。

### 3.3 社交角色

[角色定义](../../../src/data/personas.js)中目前有 13 个社交角色：露娜、麦克斯、贝拉、奥利弗、苏菲、初音未来、雷姆、远坂凛、漩涡鸣人、L、零二、亚丝娜、五条悟。

当前已有：

- 人格、兴趣、作息、在线状态、情绪和亲密度等基础字段。
- 本地长期记忆与相关记忆注入。
- 朋友圈、点赞/评论、节日/生日动态等现有 UI 与本地逻辑。
- 群聊每个用户回合只选择一位角色回复，避免并发 fan-out。

当前不足：

- 多个角色没有同等完整、可测试的显式系统提示词，通用身份拼装容易让角色语气趋同。
- 主动问候主要来自 [GreetingService](../../../src/core/presence/GreetingService.js) 的通用本地模板，不会维护角色自己的连续日常经历。
- `_handleAISchedule` 仍是网页内存中的 `setTimeout`，最长 24 小时，刷新或关闭网页后不可靠，并发送统一文案。
- 朋友圈已有丰富表面功能，但人物发帖、私聊、记忆和后续对话尚未形成同一套连续生活状态。

### 3.4 当前通知能力

- [NotificationContext](../../../src/context/NotificationContext.jsx) 使用页面内 `new Notification()`；只有应用仍在运行且页面隐藏时才可能通知。
- [Service Worker](../../../public/sw.js) 目前只处理缓存与离线请求，没有 `push` 和 `notificationclick` 事件。
- 当前已有全局声音、免打扰和浏览器通知字段，但还没有完整的后台订阅、安静时段、通知预览和服务端调度。
- UI 中已有聊天静音入口，但需要在未来通知管线中真正统一执行。静音不能只停留在界面字段。

## 4. 共同设计原则

以下原则贯穿已经确认的方案：

1. **能力优先**：保留长上下文、完整当前输入、正常输出预算和真实工具能力。
2. **固定模型**：普通聊天和后台规划默认使用一个明确的 OpenRouter 模型 ID；不使用 `openrouter/free`、`openrouter/auto` 或隐藏 fallback 列表。
3. **减少 fan-out**：一次后台唤醒批量评估多个候选角色，并在同一次响应中生成最终动作和文案。
4. **允许不行动**：模型必须可以返回 `no_action`，随机唤醒不等于强制制造内容。
5. **本地门控优先**：时间、静音、频率、关系状态和明显事件先由确定性逻辑判断，满足资格后才调用模型。
6. **工具必须真实**：不可执行、伪造或只有占位输出的工具不应展示给用户。
7. **主动行为可解释、可关闭、可撤销**：用户能看到角色记住了什么、何时会跟进，并能修改或取消。
8. **静音不等于停用角色**：静音只抑制系统通知；“关闭主动活动”才停止自主消息和朋友圈生成。
9. **持续记忆而非随机失忆**：朋友圈、私聊和后续对话共享稳定人物经历，避免同一天发生互相矛盾的虚构事件。
10. **真实验收**：固定场景、真实模型、真实浏览器、真实通知/时间推进和可复核证据缺一不可。

## 5. 已确认设计 A：总体架构与请求链路

```text
用户消息
   ├─→ 长上下文 + 记忆 → 固定 OpenRouter 模型 → 正常角色回复
   └─→ 事件识别 → 待跟进事件 → 后台调度 → Web Push
                                             ↓
                                      点击进入对应聊天
```

已确认的行为：

- 普通聊天只调用当前固定文本模型 1 次，不并发调用其他模型。
- “我明天考试”这类明确事件由本地规则识别并登记，不增加当前回合的模型请求。
- 时间或意图确实含糊时，允许当前模型调用 `schedule_follow_up` 一类结构化工具；整个可见回合最多 2 次模型请求。
- 长上下文和正常模型能力保留，不通过粗暴截断换取低 token 数。
- 后台调度与通知使用稳定事件 ID；点击通知进入对应聊天，重复推送或重复同步不会插入两条消息。
- 聊天内显示轻量确认条，例如：`露娜会在明晚问你考试情况 · 修改 · 取消`。
- 完整普通聊天仍以本地存储为主；后台只取得完成自主行为所需的授权数据。

基础请求预算：

| 场景 | 模型请求预算 |
|---|---:|
| 普通聊天 | 1 |
| 明确事件识别并安排 | 当前回复 1；本地登记 0 额外请求 |
| 含糊事件需要模型工具判断 | 整个当前回合最多 2 |
| 没有候选人的后台窗口 | 0 |
| 有候选人的一次后台批量规划 | 1 |
| 多个角色参与同一后台窗口 | 仍为 1 次批量规划，不按角色 fan-out |
| 到期事件的个性化跟进 | 最多 1；可以和同一窗口其他动作合并，失败时模板兜底 |

## 6. 已确认设计 B：事件记忆与主动跟进

### 6.1 事件分层

- **明确事件**：`我明天考试`。直接建立待跟进事件，并显示可撤销确认条。
- **事件明确、时间不明**：`我过几天要面试`。角色只在自然对话中追问一次；没得到时间则只记忆，不通知。
- **假设或低置信度**：`我可能会参加考试`。只作为短期记忆，不安排通知。
- 过去事件、泛泛讨论和其他人的事件默认不创建跟进。

### 6.2 时间语义

- 有明确结束时间：一般在结束后 1～2 小时询问。
- 只有日期：按事件类型选择当天傍晚或晚上；“明天考试”默认第二天约 20:00。
- 用户给出明确跟进时间时以用户要求为准。
- 默认安静时段 22:00～08:00；落入安静时段的通知顺延或留在应用内。
- 使用设备时区，并在实现与测试中覆盖跨时区和夏令时变化。

### 6.3 生命周期和行为上限

```text
识别 → 待确认 → 已安排 → 已生成 → 已通知 → 已打开 → 已回应 / 已过期
             ↘ 修改
             ↘ 取消
```

- 每个事件最多主动询问一次；用户不回复就不继续追问。
- 同一角色短时间内有多个到期事件时合并为一条自然消息。
- 一个事件只由当前聊天角色跟进，其他角色不围绕同一事实并发问候。
- `不用提醒了`、`考试取消了` 会取消事件；`改成下周考试` 更新原事件而不是创建重复事件。
- 通知、待同步消息和本地聊天使用同一事件 ID 做幂等合并。
- 原始事件摘要进入后续相关对话上下文，让角色知道自己为什么询问。
- 已确认的初始默认值为：每个角色每天最多一次主动私聊，全局每天最多两次；这些值可在真实 UX 测试后调优。
- 无事件的“好久不见”默认只在应用打开后展示；只有用户启用更活跃模式时才允许成为后台私聊候选。

## 7. 已确认设计 C：受约束的自主社交与朋友圈

用户明确修正了“后台完全不运行模型”的早期方向。最终确认的方向是：后台可以合理唤醒模型，并让模型自行决定是否行动。

```text
随机候选窗口
      ↓
确定性资格门控
      ↓ 有候选角色才请求
单次固定 OpenRouter 模型批量规划
      ↓
no_action / direct_message / event_follow_up / moment_post
```

### 7.1 资格门控

在调用模型前检查：

- 用户是否允许主动活动。
- 全局免打扰、安静时段、逐聊天静音和通知权限。
- 角色最近互动时间、亲密度、未完成事件、作息和个体主动程度。
- 当日主动次数、最近是否刚联系过、用户是否长期没有回应。
- 由稳定种子和时间抖动产生的随机概率，避免进程重启后重复执行或所有角色整点出现。

没有候选角色时不调用模型。

### 7.2 单次结构化规划

规划响应的工作草案：

```json
{
  "actions": [
    {
      "personaId": "ai-1",
      "type": "no_action | direct_message | event_follow_up | moment_post",
      "content": "...",
      "notify": true,
      "deliverAt": "2026-08-15T20:07:00+08:00",
      "memoryPatch": {}
    }
  ]
}
```

- 同一次请求同时完成行为选择、最终文案和必要记忆更新，不再追加一个“润色模型”。
- 模型可以对全部候选返回 `no_action`。
- 同一次批量结果可以包含一条朋友圈、少量其他角色点赞/评论和一条私聊，但必须遵守全局上限。
- 朋友圈、私聊和角色短期记忆共享“当日生活状态”。例如角色发过“去书店”，后续聊天中应记得，而不能随机改成同一时段在其他地点。

### 7.3 默认活跃度

已确认三个等级：

| 模式 | 默认行为 |
|---|---|
| 安静 | 只有明确事件跟进 |
| 自然 | 默认；每天 1～3 个随机候选窗口，资格通过后最多 2 次无事件模型调用 |
| 活跃 | 允许更多问候与朋友圈；具体上限尚待 UX 测试 |
| 关闭主动活动 | 角色只在用户发消息后回应 |

自然模式的初始内容上限：

- 私聊问候全局每天 0～2 条。
- 朋友圈全局每天 0～3 条。
- 明确事件跟进不占普通问候额度，但一个事件仍只跟进一次。
- 用户长期不回应时主动概率递减，不以负面话术催促用户回来。

### 7.4 朋友圈与通知

- 朋友圈默认只显示应用内红点，不发送系统通知。
- 私聊、明确事件跟进和未来可能的“提及用户”才是通知候选。
- 任务 Agent 默认不发布虚构生活朋友圈；只有社交角色拥有完整日常动态能力。
- 任务 Agent 未来只能在用户授权后发送学习提醒、任务进度或计划跟进。

## 8. 已确认设计 D：后台、通知、身份与隐私

### 8.1 参考后台架构

```text
PWA / IndexedDB
       ↕ HTTPS
Node API + PostgreSQL
       ├─ 调度 Worker
       ├─ OpenRouter 自主规划器
       └─ Web Push 投递器
```

- API 与 Worker 使用同一套业务代码，可作为不同进程部署。
- PostgreSQL 保存计划任务和投递状态；首版不额外引入 Redis。
- Worker 按固定短周期领取到期任务，通过数据库锁和 `dedupeKey` 防止多实例重复执行。
- 随机行为提前安排候选窗口；到点先门控，不持续轮询模型。
- OpenRouter 不可用时，明确事件使用角色模板兜底；随机问候直接跳过，不在恢复后集中补发。
- 没有后台时普通聊天仍可使用，只是不具备网页关闭后的主动模型和 Web Push。

### 8.2 服务端最小数据

已确认服务端不保存完整普通聊天和用户客户端 API Key。后台只保存：

- 匿名设备与 Push 订阅。
- 待跟进事件和状态。
- 角色关系、最近互动时间和用户授权的短期“角色记忆胶囊”。
- 尚未同步到本地的自主私聊、朋友圈与通知状态。
- 主动等级、静音、免打扰、时区和预览设置。

记忆胶囊示意：

```json
{
  "personaId": "ai-1",
  "relationshipStage": "familiar",
  "recentMood": "nervous_about_exam",
  "openEvents": ["math exam tomorrow"],
  "lastInteractionAt": "...",
  "safeMemorySummary": "用户最近在准备数学考试"
}
```

- 关闭云端自主活动后，应删除记忆胶囊并取消随机任务，不删除本地聊天。
- 待同步私聊默认在同步成功后短期保留，最迟 30 天清理。
- 设置中提供“删除云端活动数据”。

### 8.3 混合身份模式

- 默认无需账号，首次启用后台时生成随机 `deviceId` 和 256 位设备令牌。
- 服务端只保存令牌哈希，Push 订阅绑定匿名设备。
- 未来登录后可以认领并合并匿名设备的事件、角色关系和朋友圈；稳定对象 ID 用于去重。
- 首版不展示不能使用的占位登录入口。

### 8.4 微信式开关语义

四类设置互相独立：

| 设置 | 语义 |
|---|---|
| 主动活动 | 是否允许角色自行私聊或发朋友圈 |
| 后台通知 | 是否显示系统 Push |
| 聊天静音 | 消息仍产生并计未读，但该聊天不弹系统通知 |
| 免打扰/安静时段 | 消息保留，通知延后、汇总或不提醒 |

- 支持静音 1 小时、8 小时、1 天或永久。
- 通知预览支持：完整内容、只显示角色名、隐藏角色和内容。
- 不在首次打开应用时突然申请浏览器权限；在首次成功安排跟进或用户主动打开后台通知时，以明确按钮请求。
- Service Worker 未来需要处理 `push` 和 `notificationclick`，点击后进入具体聊天并携带事件 ID。

参考标准：

- [MDN Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API)
- [MDN ServiceWorkerRegistration.showNotification](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerRegistration/showNotification)
- [MDN PushManager.subscribe](https://developer.mozilla.org/en-US/docs/Web/API/PushManager/subscribe)

### 8.5 安全与可靠性

- 后台 OpenRouter Key 和 VAPID 私钥只存在服务端环境变量，不提交仓库或返回浏览器。
- 本机 crouter 中的 Key 只能在实施/测试时通过安全方式读取并注入；禁止输出、写日志、保存快照或写进文档。
- API 需要严格结构校验、设备鉴权、速率限制和请求大小限制。
- Push 载荷只带路由所需 ID 和用户允许显示的预览。
- 失效订阅自动停用；投递有限重试，不无限循环。
- 撤销权限、关闭主动活动或删除云端数据后，后台立即停止对应任务。

### 9.1 通用工具契约待确认

### 9.2 各 Agent 待讨论方向

#### Coder

- `analyze_code` 要支持哪些语言、输入规模和诊断类型；是浏览器 AST 分析、服务端分析还是只做模型审查。

#### Muse

#### Scholar

- Tavily 搜索、事实核查和深度研究的证据卡片、来源域过滤、引用格式与时间敏感性。

#### Sensei

- 学习进度、错题、掌握度与学习计划应保存哪些数据。

- 是否允许把考试/复习计划接入已确认的事件跟进引擎。

#### Aurora

- 把呼吸练习实现成真正的计时交互卡，而不是静态字符串。
- 情绪日志的数据结构、趋势展示、删除/导出和隐私边界。
- 危机或自伤语境的安全流程、地区资源和不得越界的医疗表述。

#### Pixel

- 增加对比度检查、可访问性色彩验证、设计 brief 与布局建议等确定性工具。
- 是否支持用户上传截图后的视觉评审；当前链路是否具备真实视觉模型能力必须先验证。
- 图片生成的费用、模型、失败兜底、缓存和内容安全策略。

## 16. 尚未讨论完：实际测试与验收

用户明确要求“实际测试网页体验”和“像真实用户一样对话”，所以不能只跑单元测试。详细矩阵仍需讨论，但至少应覆盖：

### 16.1 自动化测试

- 事件识别：明确、含糊、假设、过去、取消、改期和重复事件。
- 时间：设备时区、跨时区、夏令时、安静时段、月底和浏览器休眠。
- 调度：假时钟、数据库锁、重试、重复 Push、幂等同步和过期任务。
- 设置：逐聊天静音、全局免打扰、关闭主动活动和通知预览。
- Service Worker：订阅、`push`、`notificationclick`、离线点击和路由恢复。
- 身份：匿名设备、令牌失效、未来登录认领与重复数据合并。
- Prompt benchmark：请求上限、固定模型、无 fallback、工具 schema、角色区分和 `no_action`。

### 16.2 真实浏览器场景

至少完成：

1. 用户对露娜说“我明天考试”，确认条出现且时间合理。
2. 关闭网页并等待后台任务；真实系统通知出现。
3. 点击通知进入正确聊天，只插入一条角色消息。
4. 用户说“考试取消了”，后台任务消失且不再通知。
5. 静音角色后仍产生应用内消息，但系统不弹通知。
6. 关闭主动活动后随机私聊和朋友圈均停止，明确设置状态可见。
7. 自然模式运行多个候选窗口，验证并非每次都行动，也不会多个角色整点围堵。
8. 朋友圈内容在后续聊天中被同一角色正确记住。
9. 权限拒绝、上游 429/5xx、Push 订阅失效和网络离线都有诚实降级。
10. 检查桌面与移动尺寸、键盘、读屏名称、焦点和减少动画。

### 16.3 真实对话验收

- 6 个任务 Agent 各完成至少一个真实工具任务，并验证工具结果而不是只评价语言风格。
- 13 个社交角色都进行多轮对话；固定相同问题对比人格差异、记忆和语气。
- 使用包含姓名、宠物、日期、偏好、考试和后续改期的长对话验证记忆。
- 模拟真实用户表达，不只使用“请展示你的全部功能”这类测试提示。
- 保存网络请求数、请求模型 ID、工具调用记录、页面最终状态、控制台和必要截图；敏感 Key 不得进入 trace 或截图。
